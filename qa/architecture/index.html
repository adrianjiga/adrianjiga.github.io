Test Automation Architecture

Six repositories that look independent on GitHub but behave as one system. This page documents how they fit together, which decisions were deliberate, and what is still wrong with them.

The repositories

  • adrianjiga.github.io The system under test. Self-hosted helper pages that replicate common interaction patterns — buttons, a CRUD table, a registration form with a custom date picker and cascading dropdowns.
  • CypressAutomationExample UI, API and table coverage in Cypress. Page objects as object literals.
  • PlaywrightAutomationExample The same surface in Playwright, plus a browser × viewport project matrix.
  • SeleniumAutomationExample The same surface in Java — Selenium, TestNG, REST Assured, Allure.
  • WebQualityAnalyzer A browser extension for accessibility, SEO and performance analysis — which also publishes its engine as a plain browser bundle, so test suites can inject it.
  • TestSuiteVitals private A CLI that retroactively ingests CI artifacts and surfaces flaky tests. Zero infrastructure — it reads what CI already produced.

Three edges, three different integration mechanisms, and each one is a deliberate choice:

EdgeMechanismWhy
Suites → site data-cy attributes over HTTP A published contract. The only coupling that is allowed to exist.
Suites → analyzer npm github: dependency (JS) / build-time fetch (Java) One engine, three consumers. Nothing is vendored, so nothing drifts.
Suites → analytics CI artifacts, read after the fact No push, no service, no coupling. Suites do not know the analyser exists.

The contract: data-cy

Every element a test touches carries a data-cy attribute, and that attribute is the only thing the suites are permitted to select on. No ids, no label[for=…], no CSS classes, no XPath.

This is the load-bearing decision in the whole portfolio, because it converts an implicit dependency into an explicit one. Ids and class names exist to serve the page — they get renamed when the markup is refactored, and under a class-based test suite that refactor silently breaks tests that had no business caring. A data-cy hook has exactly one purpose, so changing one is unambiguously a breaking change to a published interface.

The proof arrived when the entire portfolio was converted to camelCase. Renaming ~30 DOM ids and every CSS class on the helper pages touched nothing in the three suites, because no suite had ever been allowed to depend on them. The hooks were a separate, deliberate migration.

The consequence nobody mentions

A contract with two sides in different repositories cannot be changed atomically. The suites run against the deployed site, so there is no merge order that avoids a red window:

  • Merge the site first → suites fail until their PRs land.
  • Merge the suites first → they fail until the site deploys.

Site-first is the better of the two, because the failure is loud and expected rather than a passing suite asserting against markup that no longer exists. During the hook migration this played out exactly as predicted: the site merged at 17:36:56, CI fired at 17:37:28–17:38:06, and the runs straddled the GitHub Pages deploy. Playwright failed twice and passed on its third attempt; Cypress landed a few seconds too early and passed on re-run.

That pattern normally means a retry is masking a real defect. Here it did not — but the only way to know was to check the deployed bytes and the run timestamps rather than accept a green tick. A retry that hides a deploy race and a retry that hides a genuine bug are indistinguishable from the summary screen.

One pattern, three idioms

All three suites implement the Page Object Model, and all three look idiomatic for their ecosystem rather than like a translation of one another:

CypressPlaywrightSelenium
Page object Exported object literal Class with a page field Class taking WebDriver + WebDriverWait
Chaining return this return this (async) return this
Waiting Built-in retry-ability Auto-waiting locators Explicit WebDriverWait
Parallelism Per-spec processes Workers × projects TestNG parallel="classes"

The Selenium suite is capped at class-level parallelism on purpose: its base test holds driver and wait as instance fields, which is safe per class but would race under method-level parallelism. Raising that ceiling means introducing a ThreadLocal<WebDriver> first — a real change, not a config flag, and the kind of limit worth writing down before someone discovers it as flakiness.

Accessibility as a shared engine

Rather than three suites each adopting a different accessibility library, all three inject the same bundle from WebQualityAnalyzer — the engine that already backs its browser extension. SEO and performance analysis are switched off: they audit the page, not the behaviour under test, and a missing meta description is not a defect of a test fixture.

Getting a browser bundle into three ecosystems takes three mechanisms, and each has a trap:

  • Playwright — addScriptTag with a resolved package path.
  • Cypress — read the file in Node, inject a <script> element into the AUT window. win.eval() also works, but only because a method call on win is an indirect eval; a bare eval() would evaluate in local scope and the global would never appear.
  • Selenium — the bundle is fetched at build time by Maven and injected as a <script> element. It cannot be handed to executeScript directly: Selenium wraps scripts in an anonymous function, so the bundle's top-level var would become a local that vanishes on return.

Java has no npm, so the analyser is downloaded during the build rather than vendored into the repository. A committed copy would be a second source of truth that goes stale the moment the analyser changes, with nothing to notice.

Baselines that shrink

Each page declares its known accessibility issues, and the assertion runs in both directions: a new issue fails, and a baseline entry that no longer occurs also fails.

Without the second direction, a baseline is just a suppression list: it only ever grows, and nothing ever tells you an entry went stale. With it, fixing a page forces the baseline to shrink.

All baselines are currently empty, so the pages are held at zero. That is only meaningful because it was checked: an empty baseline passes just as happily when the audit is silently returning nothing. Injecting an <img> with no alt moves the score from 100 to 97 and produces a finding, which is what makes the zeros evidence rather than an assumption.

Reading the results back

TestSuiteVitals ingests what CI already uploaded — JUnit XML, Playwright blob reports, mochawesome JSON — and reconstructs reliability history without any service to run. Two decisions carry it:

  • Test identity is hash(file + title_path). Not the display name, and never the suite label. When a TestNG suite name leaked into the file field, a single test fragmented into three identities and its history silently split.
  • The dedup key is (run_id, run_attempt, id, matrix), and the matrix is deliberately not part of identity. Same test, two browsers, is one test with two results — not two tests. Before the matrix was populated, a Cypress run parsed 3,360 results and stored 720: everything but the last browser was silently overwritten, which made browser-specific failures invisible.

The rule that keeps reappearing

One theme surfaced in every repository, in a different disguise each time:

A fact that lives in two places diverges. The only reliable fix is to delete one of them.
Duplicated factHow it went wrongResolution
Docker image tag and npm dependency version Two pins for one version; they disagreed Derive the image tag from the dependency
Coverage numbers transcribed into READMEs Stale the moment a test was added State where the truth lives instead of copying it
Analyzer bundle, if vendored per repo Three copies aging independently One published artifact, fetched at build time
DOM ids and data-cy hooks as selectors Two parallel contracts, only one of them intentional Hooks only; ids became implementation detail
Lint config contradicting the house naming style Identifiers renamed to satisfy a tool default Reconfigure the rule — the convention dictates the config
A docstring restating what the code does Documented rule was the inverse of the implementation Correct it, and prefer describing why over what

What CI actually proves

Green is not the same as verified, and three specific failures here looked like passes:

  • Jobs that skip look like jobs that pass. A workflow's own path filters excluded .github/workflows/**, so changing the test workflow never ran the tests that would validate it. The PR showed skipping in a list of green ticks.
  • An artifact glob that stops matching fails silently. A merge job collected shards with a wildcard; a rename would have kept matching the sharded blobs while quietly dropping the responsive ones. Nothing errors — the report is just incomplete.
  • A verification can inherit the bug it is checking for. A migration missed single-quoted attribute values inside double-quoted selectors, and the grep written to verify it had the identical blind spot, so it reported clean. Only loading the page found it.

Known gaps

Documented deliberately, because a portfolio that claims to be finished is less credible than one that knows what it is missing:

  • Selenium is Chrome-only. The base test constructs ChromeDriver directly. Cross-browser needs a driver factory reading a -Dbrowser= property.
  • Selenium cannot run method-level parallel until the driver moves to a ThreadLocal.
  • Smoke coverage is thin — the Playwright @smoke tag selects a single test, which is too narrow to gate a merge on.
  • API tests assert literal values where they should assert schemas, so a response shape change can pass as long as the sampled fields survive.
  • Accessibility coverage audits rendered states, not journeys. Each page is checked at load and, for the form, after submission — but not mid-interaction with a dropdown open.
